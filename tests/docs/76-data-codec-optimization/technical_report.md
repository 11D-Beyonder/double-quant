# 76 优化数据编解码功能测试（Func-44） 技术报告

## 技术目标

功能 76 对应验收项：

```text
数据编解码优化技术
```

本功能的目标是为项目中的金融时间序列数据提供一个比 CSV 更适合程序内部传输、缓存和读写的编解码模块。该模块服务于 `double_quant.data` 数据层，重点优化以下对象：

- 股票价格矩阵
- 收益率矩阵
- 多资产结构化数值表
- 带交易日期索引的金融时间序列 `DataFrame`

## 编码格式设计

优化编解码 使用 NumPy 二进制容器保存金融数据，避免 CSV 文本格式带来的重复字符、浮点数字符串格式化和文本解析开销。

编码数据 中包含三部分：

| 组成 | 内容 | 作用 |
|---|---|---|
| `metadata` | JSON 元数据字节 | 保存格式名、版本、列名、索引名、时区、时间单位、频率等结构信息 |
| `index_values` | `int64` 时间索引值 | 保存交易日期索引，支持微秒、纳秒等 pandas 时间单位 |
| `values` | 连续 `float64` 数值矩阵 | 保存价格、收益率等金融数值，避免 CSV 文本转换 |

处理流程如下：

```text
DataFrame
  -> 校验 DatetimeIndex 与数值列
  -> 提取 columns/index 元数据
  -> 将数值矩阵转为连续 float64 ndarray
  -> 使用 np.savez 或 np.savez_compressed 写入二进制编码数据
  -> bytes / 文件
```

解码流程如下：

```text
bytes / 文件
  -> np.load 读取二进制容器
  -> 校验 metadata 的 format/version
  -> 按原始时间单位恢复 DatetimeIndex
  -> 恢复时区、索引名、列名
  -> 重建 DataFrame
```

## 关键技术点

### 1. 面向金融数据形态的窄接口

模块没有设计为任意对象 `DataFrame` 的通用序列化器，而是有意限定为：

- `DatetimeIndex`
- 数值型列
- 金融时间序列矩阵

这样可以直接服务现有 `PriceSource.fetch()`、`to_log_returns()`、风险归因和实验缓存流程，避免为对象列、混合嵌套结构等非核心需求引入复杂度。

### 2. 二进制矩阵编码

CSV 会把每个浮点数写成文本，读回时再解析为浮点数。优化编解码 直接保存 `float64` 矩阵，因此减少了：

- 浮点数转字符串成本
- 字符串转浮点数成本
- 分隔符、换行、重复日期文本带来的体积开销
- CSV parser 对列类型推断的额外开销

在 10000 行、12 列测试数据上，编码数据体积从 2,322,171 字节降到 1,041,072 字节。

### 3. 时间索引兼容

当前 pandas 版本的 `DatetimeIndex` 可能使用 `datetime64[us]`，也可能在其他场景使用纳秒单位或时区 dtype。实现中保存 `index_unit` 与 `index_timezone`，解码时按原始单位恢复日期，避免把微秒时间戳误读为纳秒时间戳。

### 4. 可选压缩模式

模块支持两种模式：

| 模式 | 实现 | 使用场景 |
|---|---|---|
| `compression="none"` | `np.savez` | 优先追求编解码速度 |
| `compression="deflate"` | `np.savez_compressed` | 优先追求更小编码数据 |

验收测试中，`deflate` 将同一组二进制 编码数据体积从 148,486 字节压缩到 133,114 字节，证明压缩路径有效。

### 5. 内置性能基准

模块提供 `benchmark_dataframe_codec(frame, repeats=...)`，直接对比同一 `DataFrame` 在 CSV 和优化编解码 下的：

- 编码数据字节数
- 编码耗时
- 解码耗时
- 体积降低比例
- 编码加速倍数
- 解码加速倍数

该基准函数被验收测试调用，也可被实验脚本复用。

## 优化效果

实测结果：

| 指标 | 未优化编解码 | 优化编解码 | 优化效果 |
|---|---:|---:|---:|
| 编解码数据体积 | 2,322,171 字节 | 1,041,072 字节 | 降低 55.17% |
| 编码耗时 | 49.184 ms | 0.184 ms | 加速 267.91x |
| 解码耗时 | 7.553 ms | 0.599 ms | 加速 12.61x |

测试断言要求：

- 优化编码数据必须小于未优化编解码数据。
- 体积降低比例必须不低于 40%。
- 编码加速必须不低于 5 倍。
- 解码加速必须不低于 1.5 倍。

这些断言使测试不仅验证功能正确，也验证性能优化确实发生。

## 技术原理补充：二进制编解码的体积与时间复杂度

CSV 编码把每个浮点数 $x$ 转换为十进制字符串，整体载荷近似为

$$
B_{csv}\approx \sum_{t,i}\ell(\mathrm{str}(p_{t,i}))+B_{date}+B_{sep},
$$

其中 $B_{date}$ 和 $B_{sep}$ 分别来自重复日期、逗号与换行。优化编码直接保存连续 `float64` 矩阵，未压缩数值部分理论大小为

$$
B_{bin}=8TN+8T+B_{meta},
$$

其中 $8TN$ 是价格或收益率矩阵，$8T$ 是 `int64` 时间索引，$B_{meta}$ 是列名、时区、频率等 JSON 元数据。对金融时间序列而言，$B_{meta}$ 远小于 $TN$ 级别的数据主体，因此规模越大，二进制矩阵编码越接近线性最优存储。

时间复杂度方面，两种方案都需要遍历 $T\times N$ 个数值；差异在常数项：CSV 需要执行浮点转字符串、字符串切分、类型推断和日期解析，而二进制路径主要执行内存连续化与 NumPy 容器写入。因此可写为

$$
T_{csv}=O(TN\cdot c_{text}),\qquad T_{bin}=O(TN\cdot c_{mem}),\quad c_{text}\gg c_{mem}.
$$

验收结果中编码加速明显高于解码加速，符合上述模型：写 CSV 的浮点格式化成本更高，而读 CSV 的 pandas 解析器已有一定优化。

## 无损性、元数据与压缩模式

无损往返的判定不是只比较字节数，而是要求解码后满足

$$
\hat{P}_{t,i}=P_{t,i},\quad \hat{\mathcal{I}}=\mathcal{I},\quad \hat{\mathcal{C}}=\mathcal{C},
$$

其中 $\mathcal{I}$ 表示交易日期索引，$\mathcal{C}$ 表示列名集合。源码中保存 `index_unit` 与 `index_timezone`，是为了避免把微秒或纳秒时间戳误解释为不同时间尺度；保存 `format/version` 是为了后续格式升级时能拒绝不兼容载荷。

`deflate` 压缩模式在 `np.savez_compressed` 上实现。它适合价格矩阵、收益率矩阵等存在局部相关性的金融数据，因为相邻交易日价格和同一列数值常具有统计冗余。压缩比可表示为

$$
\rho=\frac{B_{deflate}}{B_{bin}},\quad 0<\rho\le 1.
$$

当任务重视传输体积或归档存储时使用 `deflate`；当任务重视频繁读写缓存时使用 `none`，这体现了编解码模块在速度和体积之间提供可控权衡。

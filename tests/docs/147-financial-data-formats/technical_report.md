# 147 可视化分析工具能对接经典金融信息数据格式技术报告

## 技术目标

本功能面向“可视化分析工具能对接经典金融信息数据格式”的验收要求。金融软件对接解决的是数据来源问题，但数据进入平台后仍然可能以 CSV、Excel、JSON、Parquet、Qlib、Arrow / Feather、HDF5 等不同格式存在。如果格式处理能力和软件对接能力混在同一个界面里，验收时很难区分平台到底是在验证软件适配，还是在验证数据文件格式。因此该功能被设计为金融编程开发页面的第二步，专门展示经典金融信息数据格式的目录、读取方式、质量规则、字段映射和验证结果。

## 为什么这样实现

经典金融信息数据格式具有明显的多样性：CSV 和 Excel 便于人工查看，JSON 适合结构化接口交换，Parquet 和 Arrow / Feather 适合列式分析，Qlib 适合量化研究目录，HDF5 适合大规模二进制数据存储。不同格式的读取方式、字段组织方式和质量风险不同，因此需要一个独立的可视化治理步骤，让用户在进入编程分析前先确认数据结构是否满足平台要求。

该实现没有只做格式名称列表，而是把格式说明、读取方式、适配场景、质量规则、标准字段映射和样例数据放在同一工作区中。这样做的原因是：格式名称只能证明“列出了格式”，而读取方式和质量规则才能证明平台理解这些格式如何被使用；字段映射和样例数据才能证明格式能够转化为后续算法可识别的数据结构。

## 功能组成

界面覆盖 CSV、Excel、JSON、Parquet、Qlib、Arrow / Feather、HDF5 共7类经典金融信息数据格式。左侧格式目录用于选择格式类型，右侧详情区域展示当前格式的文件形态、读取方式、适配场景和质量规则。字段映射表用于说明源字段如何映射到平台标准字段，样例数据表用于展示转换后的数据形态。

页面顶部保留三步流程导航，用户可以明确知道当前处于“数据格式”步骤。这样既避免长页面滚动带来的认知负担，也把 146 的软件对接、147 的格式治理、149 的金融编程执行拆成三个验收边界清晰的功能点。

## 字段与质量规则设计

该功能沿用第一步输出的标准字段模型，包括证券代码、交易日期、开盘价、最高价、最低价、收盘价、成交量、成交额和复权因子。不同文件格式可以有不同的源字段名，但进入平台后都需要映射到同一组标准字段。这样后续金融编程模块只依赖标准字段，不需要关心源文件是 CSV、JSON 还是 Parquet。

质量规则围绕金融时间序列数据的常见风险设计，包含字段完整性、交易日期排序、价格数值类型和关键字段空值检查。选择这些规则的原因是：缺字段会导致算法无法读取输入；日期乱序会影响收益率、回测和窗口计算；价格字段不是数值会导致计算失败；关键空值会影响估值结果和概率分布解释。

## 交互与状态流转

用户从第一步生成标准数据后进入第二步，在左侧选择目标格式。格式切换后，文件形态、读取方式、适配场景、质量规则、字段映射和样例数据同步变化。点击“验证数据格式”后，页面展示校验通过状态，说明当前数据格式满足后续金融编程步骤的基础要求。

这种状态流转体现了“格式识别、结构解释、质量检查、标准化确认”的过程。它不是单纯显示静态文档，而是让用户通过选择格式和点击验证入口完成一次可视化确认。

## 验收关注点

本功能的验收重点包括：是否覆盖经典金融信息数据格式；是否展示格式读取方式和适配场景；是否展示质量规则；是否展示标准字段映射；是否提供样例数据预览；是否具备数据格式验证入口。截图中展示了7类格式，并对格式目录、验证入口和校验结果进行了标注，能够支撑 UI 操作型验收。

## 技术边界

本功能关注格式接入和结构治理，不在技术报告中展开文件上传、批量解析、大文件分片、后端存储等安装部署或运行流程。真实业务扩展时，可以在统一数据读取服务中承接大文件、目录型数据集和二进制数据容器，但前端验收的核心仍然是格式目录、读取语义、字段映射和质量规则是否可见、可检查。

## 技术结论

该实现把经典金融信息数据格式处理拆成独立步骤，通过7类格式目录、读取方式、质量规则、标准字段映射、样例数据和验证入口，证明平台具备面向常见金融数据格式的可视化接入与治理能力。其设计重点是将多格式差异转化为统一字段模型和质量检查结果，为后续金融编程提供可信输入。
